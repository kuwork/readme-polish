## 关键词研究

动笔前先归纳两档关键词，全程自然布局、不堆砌（同一词自然出现一次即可，重复堆砌会被搜索引擎和读者同时惩罚）：

- **主关键词（1–2 个）**：项目品类 + 宿主/平台，例如 `DeepSeek Harness plugin`、`Markdown kanban board`、`VS Code extension for …`。来源：包名、`package.json` 既有 keywords、上游生态的叫法。
- **次级关键词（5–10 个）**：用户搜索时的同义与场景词，例如技术范式（`git-native`、`local-first`）、相邻工具名（`Claude Code`、`Codex`，仅在确有集成时写）、品类词（`task management`、`developer tools`）、语言/运行时。
- 校验方法：在 npm/GitHub 搜索框输入主词看下拉联想，对照同类高星包的 keywords 与标题用词；只保留与项目真实能力相符的词，不蹭无关热词。

## 关键词布局位置

按搜索权重从高到低布局，每处只做自然提及：

| 位置 | 做法 |
|---|---|
| H1 紧接的副标题 | 一句话含主关键词，说明是什么、为谁服务 |
| 首段前 160 字符 | 主词 + 1–2 个次词自然成句；这是 Google 摘要与 AI 抽取最常引用的片段 |
| H2 / H3 标题 | 能用问句就用问句（「如何关闭自动安装？/ How do I disable auto-install?」），命中用户搜索原句 |
| Features 条目 | 每条承载一个相关词，绑定具体能力而非堆词 |
| 图片 alt | 描述画面时带上品类词；每张图 alt 不重复 |
| 代码块注释 | 命令旁的注释会被索引，可写含关键词的简短说明 |
| 文档尾段/License 前 | 自然补充长尾词，不要集中词块 |

标题同时面向人类扫读：同一层级保持统一大小写风格，避免营销化空洞标题。

## 内容长度与结构信号

- 工具/库类 README 目标 500–1500 词（中文约对应更紧凑的信息量，以章节完整为准），少于 200 词的结构化评分显著偏低；长度靠信息密度而非注水。
- 显式 H2 层级 + 顶部点式导航（长文同时给目录），让搜索引擎和 AI 能抽取内容大纲。
- 表格承载对照型信息（配置项、入口、版本差异），列表承载同构条目（Features、限制），折叠块承载参考型细节。
- 每个 H2 小节尽量自包含：单独被抽取阅读时也能读懂，第一节第一句先给结论。

## npm 包元数据清单

README 之外，同步检查 `package.json`（其他生态对照等价字段）：

- [ ] `description`：一句话完整句，含主关键词；理想约 128 字符、GitHub/npm 硬限约 350 字符；不要以「A simple…」开头。
- [ ] `keywords`：10–20 个相关词，主词/次词/场景词混合，去重；与 README 用词保持一致。
- [ ] `files`：确认 `README.md`、所有语言变体（如 `README.en.md`）、README 引用的图片目录（注意区分 `*.jpg` 与 `*.png` glob）、`LICENSE` 都在清单内。
- [ ] `repository` / `homepage` / `bugs` 三个 URL 完整填写，构成仓库与包之间的反向链接。
- [ ] `engines` 等运行时约束与 README 中的前置条件、badge 数字一致。
- [ ] 改完跑 `npm pack --dry-run`，核对 tarball 内文件与包体积；截图/banner 异常增大包体积时提示用户权衡。
- [ ] 只动文档与元数据字段；名称、版本号、依赖、导出入口等不得借 README 优化之名改动。

Python（`pyproject.toml` 的 description/keywords/classifiers）、Rust（`Cargo.toml` description + keywords）、Go（仓库描述为主）按同原则映射。

## GitHub 仓库侧设置（需提醒用户手动）

以下项不在仓库文件内，无法代改，交付时明确提醒并给出建议值：

- [ ] **About 简介**：与 README 首段同义的一句话 + 官网/文档直链；它决定社交卡片与搜索摘要。
- [ ] **Topics 标签**：用满最多 20 个，语言标签（`javascript`、`python`）与功能标签（`kanban`、`task-management`、`ai-agent`）混合。
- [ ] **社交预览图**：如仓库设置支持自定义 social preview，使用与 README banner 同视觉的图。
- [ ] **Description 中的外链**：指向官方文档站可形成双向权重。

## AI 引用优化

ChatGPT、Perplexity、AI Overviews 等倾向抽取结构化、可直接引用的内容：

- **Answer-first**：每节/每个 FAQ 第一句就是结论，细节放后面。
- **显式对比与具体数字**：「比 X 少一个进程」「超时默认 90000ms」「支持 7 类目录判定」比「快速」「强大」更易被引用；数字必须真实可核。
- **自包含小节**：配置表、FAQ 单条脱离上下文也能读懂。
- **术语一致**：同一事物全程同名（包括大小写与标点），中英双语之间维护术语对照表，避免 AI 抽取时混淆。
- **事实可溯源**：命令、默认值、路径与代码/CLI 实际行为一致；过时示例会同时摧毁人类与 AI 的信任。

## 双语文件命名与互链

- 优先跟随宿主项目或生态的既有约定；无约定时：
  - 英文默认（国际 SEO 优先）：`README.md`（英文）+ `README.zh-CN.md`（中文）。
  - 中文默认：`README.md`（中文）+ `README.en.md`（英文）。
- 每个文件顶部放切换行：当前语言纯文本、其他语言相对链接，例如 `简体中文 ｜ [English](README.en.md)`。
- 两份文件的章节、badge、导航、截图、事实陈述严格平行，同批修改；版本支持边界等敏感信息两边必须一致。
- 锚点按各语言 GitHub slug 规则生成（小写、空格转连字符、去除标点、保留 Unicode 字母与汉字）；不要假设中英文锚点逐字对应。
- 语言文件加入发布清单并验证互链在 npm/GitHub 两侧都可达。

## 发布前核对表

- [ ] `node scripts/check_readme.mjs <项目目录>` 退出码 0：无断链锚点、无缺失本地图片、语言互链文件存在。
- [ ] 包发布 dry-run（如 `npm pack --dry-run`）包含全部 README、语言文件与图片。
- [ ] badge 链接实际可打开，数量 ≤ 6，无只在 tag 触发的 CI 状态 badge。
- [ ] 所有外部链接指向真实页面；无法核实的链接宁可删掉，不编造官网。
- [ ] 推送到分支后在 GitHub 网页渲染验证：alert 块、`<details>`、中文锚点、`<div align>` 居中、移动端表格；逐条点击导航。
- [ ] 双语对照无事实漂移；术语、命令、默认值、版本占位符一致。
- [ ] 提醒用户手动完成 GitHub About、Topics、social preview 设置。
- [ ] Git 操作遵守用户确认规则：未确认不提交；提交时精确暂存文件、不擅自创建或推送 tag。
